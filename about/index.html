About Maria Gilca

I'm a technical writer and information architect. I work on data-intensive software, currently at OpenLM, where documentation has to describe systems that change underneath it.

Most of my work starts as something that doesn't look like a documentation problem. Two dashboards disagree. An approval process stalls. The help centre describes a feature nobody recognises. Underneath, the same thing is usually true: a concept has collected more than one name, and nothing in the system is responsible for deciding which one is correct.

What I actually do​

  • Information architecture. Mapping the entities, data flows and decisions before writing a page, because for a data-heavy product the useful structure follows the data, not the table of contents.
  • Definitions with owners. One agreed name per concept, the rejected alternatives kept so old vocabulary still leads somewhere, and the reasoning recorded so the question isn't reopened every quarter.
  • Metadata standards that make a documentation set auditable: which pages are unowned, which are overdue for review, which describe a service that no longer exists.
  • Governance covering the last mile: how an approved change reaches the product and the help centre, not just the page where someone noticed the error.
  • The pipeline itself. Docs-as-code with real gates: link and anchor validation, terminology checks, staleness flags, all in CI where the author of a change can't wave them through.

How I work with AI​

I use AI daily in my own work, I build agent workflows against docs repositories, and I've taken that from personal tooling into a team's process, which is a different and harder problem, because it needs review gates other people trust.

The short version of what I've learned: generating documentation stopped being the hard part, and verifying it didn't. So the bottleneck moved, and the system has to move with it.

  • Agents are scoped, not general. I run them with Claude Code, tools limited to the docs directory, and an MCP server for the issue tracker when the agent needs the context behind a change. The task definition lives in the repo and is reviewed like code, because it's the thing that decides what the agent is allowed to conclude.
  • The most valuable instruction is the one that says stop. An agent facing a concept with no agreed name will name it. A plausible invented name is worse than a blocked pull request, because it propagates before anyone notices it was never decided.
  • Git is the control plane. Every machine-written change arrives as a pull request with a provenance trail. Nothing writes to main, and a revert is one command rather than an archaeology project.
  • Automate the mechanical checks so humans review claims. When draft volume goes up tenfold, review is the constraint. A reviewer's attention should go to whether something is true, not to dead links and trailing whitespace.
  • AI amplifies the information architecture you already have. If a concept has three names and no owner, an agent will use all three, faster, across more pages. This is why I front-load structure: it decides whether automation compounds or just accelerates the mess.

I've written the full split (what I hand to an agent, what CI has to catch, and what I refuse to automate) on the practice page.

How I work with teams​

I interview engineers, product managers and support, and I read incident notes, which are the most honest documentation an organisation has, because they record what happened rather than what was supposed to. Then I write something, show it to the person who will have to use it, and find out where it breaks.

The part I care about most is what happens after I leave. Documentation only one person can maintain is a liability wearing a deliverable's clothes, so the governance and the metadata are not paperwork around the writing; they are the writing.
