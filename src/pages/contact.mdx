## What's useful to include

You don't need a specification. A paragraph is plenty. The things that help me
give you a straight answer rather than a discovery call:

- **What's going wrong, in the form you noticed it.** "Two teams report different
  numbers for the same metric" is more useful than "we need better docs": the
  first one tells me where to look.
- **Who has to use the result.** Engineers, support, customers or auditors. These
  want genuinely different artefacts, and the difference is not cosmetic.
- **Where you are with AI**, if it's part of the question. Whether you're
  generating drafts already, whether anyone reviews them, and whether anything
  currently stops a wrong page reaching production. That last one usually decides
  the shape of the work.
- **Your timeline**, including whatever is forcing it: a release, an audit, an
  onboarding wave.

## Work I'm a good fit for

Documentation that needs the same rigour as the engineering stack behind it:
information architecture for a data-heavy product, definitions that will still be
correct next year, metadata standards and governance that outlast the person who
set them up, or a docs pipeline where agents draft and CI gates catch what they
get wrong.

If you're generating documentation with AI and it's getting faster without getting
more accurate, that's a specific and fixable problem, and usually a structural one
rather than a prompting one.

If you're not sure the problem is a documentation problem, that's a reasonable
thing to ask about. Quite often it isn't, and it's cheaper to find that out in an
email.
