## Align docs velocity with product velocity

Docs-as-code succeeds only when writers share the same branching rituals as
engineers. Mirror the product repo: one `main` branch, short-lived feature
branches, and required status checks. Docusaurus plays nicely when you split
configuration (`docusaurus.config.js`, `sidebars.js`) from content, so diffs stay
readable and a reviewer can see what actually changed.

## Keep builds fast and opinionated

Add CI jobs for linting MDX, validating links, and generating preview deploys with
`docusaurus build`. Cache `node_modules` and the `.docusaurus` output so builds
feel instant: a fast signal keeps reviewers engaged, and a slow one teaches
people to approve without looking.

Two settings are worth making non-negotiable, because both only take effect in
production builds and will otherwise fail silently in local development:

```js title="docusaurus.config.js"
onBrokenLinks: 'throw',
markdown: {
  hooks: {onBrokenMarkdownLinks: 'throw'},
},
```

If a broken internal link can't fail the build, it will reach production. One
caveat if your sitemap uses `lastmod`: it is resolved from git history, so a CI
job checking out with the default shallow clone silently drops it. `fetch-depth: 0`.

## Make visual QA effortless

Writers should not have to guess how a component renders in production. Generate
preview URLs for every branch, and keep a page in the repo that renders each
shared component with real content, so the team updates it once and every page
inherits the change.

## Capture tribal knowledge in the repo

CI secrets, content strategy decisions, voice and tone guidance, launch
checklists: all of it belongs next to the content it governs. Use admonitions
(`:::tip`) to mark the things someone will otherwise have to ask about, and
include runnable snippets so a future contributor can extend your work without
messaging you.

The test of docs-as-code isn't whether the pipeline is elegant. It's whether
documentation ships in the same release as the feature it describes.
